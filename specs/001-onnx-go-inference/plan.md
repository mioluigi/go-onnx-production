**Why three small reusable packages?** Each does one job any project could reuse: `idx` reads a standard
data format, `inference` runs any single-input classifier exported to ONNX, `parity` compares two models'
outputs. None prints, opens files by name, or exits (Constitution 4.1).

## 3. Data design

**Format: IDX, the format MNIST itself is distributed in.** A short header (data type code, number of
dimensions, the size of each dimension, big-endian) followed by the raw values. The test images and labels
are the **official files, unchanged**, which avoids any conversion error. PyTorch's predictions are written
in the same format (type `0x0D`, float32), so one Go reader handles all three files.

**Input contract (FR-3a), applied identically in both languages:** each 28 × 28 image is flattened
row by row to 784 values, converted to `float32`, and divided by 255. No other normalization, so there is
nothing for the two languages to disagree about. A Go unit test checks known pixels; the full-test-set
parity check confirms the whole pipeline.

**Sizes** (NFR-6): images ~1.6 MB compressed, model and weights ~0.4 MB each, predictions ~0.4 MB. All
are embedded in the Go binary so the executables run with no other files (FR-11).

## 4. Package `inference` — the core

```go
// Model is an ONNX classifier prepared to run with GoMLX.
type Model struct { /* parsed ONNX model, weights store, compiled executor, input/output names, sizes */ }

// Load parses ONNX bytes, loads the weights, and prepares the executor (compiled on first use).
func Load(onnxBytes []byte, opts Options) (*Model, error)

// Predict returns one row of class probabilities per input row.
func (m *Model) Predict(inputs [][]float32) ([][]float32, error)

func (m *Model) NumFeatures() int
func (m *Model) NumClasses() int
func (m *Model) Close()

// (Changed in T06: Labels, the arg max that replaces ONNX's label output, lives in package parity.)
```

**Steps and reasons**

1. **Parse** with `parser.Parse`; validate one input and an output named `probabilities` (configurable),
   with a fixed feature count. *Why:* clear errors (`ErrNotONNX`, `ErrInputShape`, `ErrMissingOutput`)
   instead of a GoMLX panic deep in graph building.
2. **Fusion** stays on by default (works for PyTorch exports, spike addendum) with `Options.DisableFusion`
   for scikit-learn-style exports (finding 2). A test covers both.
3. **Load weights** into a `model.Store` with `VariablesToScope`.
4. **Compile once, run many times:** create one `model.Exec` and call it for every prediction. GoMLX
   caches the compiled graph per batch size. *Why:* `CallOnce` would recompile on every request, the
   opposite of what a production service needs.
5. **Request only `probabilities`** and compute labels in Go (finding 3).
6. **Validate inputs** (empty batch, wrong row length, NaN/Inf) before running, and **check outputs** for
   NaN/Inf. Library panics are recovered at the package boundary and returned as wrapped errors
   (Constitution 2.7).

**Backend selection:** `Options.Backend` (`"xla"` or `"go"`; empty means GoMLX's default; changed in T11, see decisions), passed to
GoMLX's backend configuration. The program exposes it as `-backend`.

## 5. Packages `idx` and `parity`

- `idx.Read(r io.Reader) (Array, error)`: detects gzip automatically; supports unsigned-byte (`0x08`)
  and float32 (`0x0D`) data; checks the magic number, dimension count, and that the data length matches
  the dimensions. Errors say what was expected and what was found.
- `parity.Compare(got, want [][]float32, tolerance float64) (Report, error)`: `Report` holds rows
  compared, labels agreeing, the largest absolute difference and where it occurred, and a non-finite
  count; `Report.Pass()` applies Q5 (100 % labels, ≤ 1 × 10⁻⁵, zero non-finite).

## 6. The program `cmd/predict-digits`

```
predict-digits                         parity check + timings on the built-in model and test set
predict-digits -input digits.csv       predict a user's images (CSV: 784 pixel values 0–255 per row)
predict-digits -model other.onnx       use another ONNX classifier (parity check needs matching data)
predict-digits -backend go|xla         choose the GoMLX backend (default xla where built in, falling back
                                       to go if XLA cannot start; go in builds without CGo)
predict-digits -runs 1000              number of timed repetitions (0 = skip timings)
predict-digits -verbose                debug logs
```

**Default output** (results on stdout, logs on stderr): model and backend, accuracy against the true
labels, parity with PyTorch (PASS/FAIL with the numbers), and timings: load, first prediction, 10,000
images in one batch (median), and one image at a time (median and 95th percentile), followed by one
parseable `benchmark …` line per measurement for `scripts/tables.sh`.

**Exit codes:** 0 success · 1 data or model problem (including a parity FAIL) · 2 command-line mistake.
`main` stays a one-liner calling `run`, as in Week 4.

**CSV validation (FR-12):** 784 values per row, each a whole number 0–255; errors name the line and value.

## 7. Testing strategy

| Test | Location | Covers |
|---|---|---|
| Synthetic ONNX models with known answers: identity-like weights, a model that always prefers one class, a two-layer network checked against NumPy; one with a 2-D bias (scikit-learn style) | `inference` | AC-2, findings 2–3 |
| Invalid model bytes, missing `probabilities` output, wrong feature count, empty batch, NaN input | `inference` | FR-12, AC-7 |
| `Labels` (arg max, ties take the first class) | `inference` | FR-3 |
| IDX: official headers, gzip and plain, truncated data, wrong magic, unsupported type | `idx` | FR-3a |
| Parity: identical inputs, differences just inside and just outside tolerance, label flips, NaN (rejected explicitly) | `parity` | FR-4 |
| Input contract: known pixel → known float | `cmd/predict-digits` or a small helper | FR-3a |
| End-to-end: build and run the binary; no args → PASS and exit 0; bad CSV → exit 1 with line number; bad flag → exit 2; logs only on stderr | `cmd/predict-digits` | AC-7 |
| Real model parity on all 10,000 test images | end-to-end test (pure-Go backend) | AC-1 |

Tests are written first and checked by deliberate breakage (Constitution 3.1). Coverage target ≥ 90 % for
`idx`, `inference`, `parity` (NFR-2).

## 8. Performance measurement design

**Units of work, identical in both languages:**

| Measure | Definition |
|---|---|
| Load | Read the model file into memory and prepare it to run |
| First prediction | The first call, one image (includes GoMLX graph compilation) |
| Bulk | All 10,000 test images in one call; median of repeated runs |
| Latency | One image per call; median and 95th percentile over 1,000 calls after warm-up |

**Python rows:** PyTorch (`torch.no_grad()`, model in eval mode) and ONNX Runtime (CPU), timed with
`time.perf_counter_ns`. **Go rows:** GoMLX with XLA and with the pure-Go backend, timed with Go's
monotonic clock in the program. All on Luis's Mac, plugged in, one session; machine details recorded.

**Monte Carlo (FR-8):** `BenchmarkPredict/batch=1 … 10000` in `inference`, random inputs with a fixed seed,
`b.ReportAllocs()`; run per backend with `GOMLX_BACKEND`.

**Profiles (NFR-3):** `go test -bench=Predict/batch=10000 -cpuprofile -memprofile ./inference/`,
summarized with `go tool pprof -top` into `results/cpu-profile.txt` and `results/memory-profile.txt`.

**Whole program (FR-10):** `scripts/measure.sh` runs `cmd/measure` on `predict-digits -runs 0` (each backend)
and `bench_python.py --predict-only` (each Python runtime): one bulk prediction including start-up.

**Tables (NFR-8):** `scripts/tables.sh` turns `results/*.txt` into Markdown for the README; times in µs
or ms, memory in MB, conversions stated.

## 9. Executables (AC-8)

| Target | How | Backend |
|---|---|---|
| macOS binary | `go build ./cmd/predict-digits` on the Mac | XLA + pure Go |
| Windows `.exe` | `GOOS=windows GOARCH=amd64 CGO_ENABLED=0 go build …` | pure Go only (build tags exclude XLA) |
| macOS `.app` | Week 4's `build-macos-app.sh`, adapted; Apple Silicon only (XLA has no Intel-Mac build) | XLA + pure Go |

**Build tags:** the XLA import lives in `cmd/predict-digits/backend_xla.go` with
`//go:build cgo && (darwin || linux)`, so a build without CGo leaves it out automatically.

## 10. Risks and mitigations

| Risk | Mitigation |
|---|---|
| The real `torch.onnx.export` produces operations not seen in the spike | T03 runs the export on the Mac first and runs the Go parity check before anything else is built on it. |
| XLA can only be tested on the Mac (its download is blocked in Claude's workspace) | Dedicated task T09 on the Mac; pure Go remains the fallback; first-run download documented. |
| Deadline (due 2026-10-25) | Core tasks first; CNN stretch goal and polish last; plan review by Gemini runs in parallel with scaffolding tasks. |
| `[][]float32` conversion cost shows up in timings | Measure first (profile); optimize only with evidence. |
